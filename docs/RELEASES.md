# Building and distributing Browser C

## Automated packages

The `Desktop packages` workflow runs when a `v*` tag is pushed or when manually dispatched from GitHub Actions. It creates platform-specific build artifacts:

- Linux: AppImage and Debian package
- Windows: NSIS installer
- macOS: DMG and ZIP

Each platform job uses the committed npm lockfile with `npm ci`, runs `npm audit --audit-level=high`, repository validation, syntax checks, and automated tests, then builds packages with Electron Builder. A staging step copies only the expected distributable package formats into `release/artifacts`, excluding unpacked application directories and builder intermediates. The workflow rejects empty packages, generates a `SHA256SUMS.txt` manifest, and validates that the expected formats exist, rejects unexpected or cross-platform artifact types, and requires every staged artifact to be listed exactly once with a matching SHA-256 digest. Only the staged packages and checksum manifest are attested and uploaded. Workflow artifacts are retained for 14 days and are not the same as a published GitHub Release.

## Verify downloaded artifacts

Keep the package and its `SHA256SUMS.txt` file together. From a Linux/macOS terminal, run:

```sh
sha256sum --check SHA256SUMS.txt
```

On Windows PowerShell, verify a named file by comparing its digest with the corresponding line in `SHA256SUMS.txt`:

```powershell
Get-FileHash .\Browser-C-0.2.0-win32-x64.exe -Algorithm SHA256
```

Use the actual filename produced by the workflow. A checksum detects accidental corruption or mismatches; it does not prove who built a package or protect against an attacker who can replace both the package and its manifest.

## Release gates and limitations

- Workflow artifacts are build outputs for testing, not stable public releases.
- The Linux Electron startup smoke test checks that the application stays alive during startup under Xvfb. It is not a full navigation, download, or private-session end-to-end test.
- macOS signing/notarization, Windows code signing, published SBOM, clean-install/upgrade testing, and installed-app launch/navigation smoke tests on Windows and macOS remain future release gates. GitHub build-provenance attestations are generated by the packaging workflow but still require a real packaging run and independent verification. Artifact validation confirms package presence and file integrity, not successful installation or runtime behavior.
- Do not advertise an artifact as a stable release until platform launch and security checks are complete.
